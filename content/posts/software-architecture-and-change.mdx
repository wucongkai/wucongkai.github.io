**好的架构把某一类需求变化限制在少数职责明确的模块中，使系统能够以较小的修改和验证成本适应变化。** “抵御”指的是控制变化带来的影响，而不是让需求停止变化，也不意味着以后无需修改代码。

这篇笔记从一个课堂问题展开：为什么 jyy 说架构设计可以抵御一部分需求变化？[《需求和架构（1）》讲义](https://jyywiki.cn/GSE/2026/lect6.md)把问题落在职责划分、数据表示和依赖关系上。以下结合本 Wiki 的改动与经典资料整理，是个人学习笔记。

本文目录：[变化如何传播](#propagation) · [Wiki 的实际例子](#wiki) · [隔离变化的机制](#mechanisms) · [课堂里的中间表示](#representation) · [为什么只能应对一部分](#limits) · [怎样评估架构](#evaluation) · [如何避免过度设计](#evolution) · [实践与资料](#practice)。

<h2 id="propagation">1. 架构影响的是变化如何传播</h2>

需求变化通常会使系统原来依赖的某个假设失效。例如，原来所有文章按日期排序，现在希望按照学习顺序排列。

如果首页、分类页和侧边栏都分别实现排序，修改要求就会传播到多个地方。某处忘记修改，用户还会看到相互矛盾的顺序。

如果它们共同调用一个定义清楚的排序模块，排序策略的改动就可以集中处理：

```text
排序规则散落各处：
新规则 → 首页的排序逻辑
       → 分类页的排序逻辑
       → 侧边栏的排序逻辑

排序职责集中：
新规则 → 排序模块 → 各页面使用排序结果
```

后者仍然要验证各个页面，但需要同步修改的规则实现更少，也更容易检查遗漏。这里的首页、分类页和侧边栏是说明传播关系的假设场景，并非本 Wiki 已经具备的全部页面。

因此，讨论架构时可以先问三个具体问题：

- **谁负责这个决定？** 例如文章展示顺序由谁确定。
- **谁依赖这个决定？** 哪些模块需要顺序，哪些模块只需要文章内容。
- **依赖者知道多少内部细节？** 它拿到最终列表，还是自己解析配置并重复排序。

文件数量、目录层级和服务数量都不能单独回答这些问题。多个文件如果共同修改全局状态、直接读取彼此的内部数据，变化仍然会跨越它们的边界。

<h2 id="wiki">2. 本 Wiki 的几次修改就是一个例子</h2>

当前 Wiki 将文章正文、排序规则、内容编译与页面展示放在不同位置。这让几类实际需求有了相对明确的落点：

| 需求变化 | 主要修改位置 | 为什么影响相对集中 |
| --- | --- | --- |
| 增加 RAG、框架与 Token 笔记 | `content/posts/` 中的文章文件 | 列表与详情页从文章数据生成，不必为每篇文章手写页面 |
| 删除两篇示例文章 | 对应文章文件 | 文章列表与静态路由随内容重新生成 |
| 按学习顺序排列三篇笔记 | `content/post-order.json` 与统一排序逻辑 | 展示顺序有明确的数据来源 |
| 为文章增加数学公式支持 | 共享内容编译模块 `lib/mdx.mjs`，以及显示样式 | 本地预览与公开文章复用编译逻辑，公式处理可以一起生效 |

这里要区分**建立能力**和**使用能力**。首次引入手动排序，仍然需要实现排序规则、编辑入口和发布支持；能力建立后，后续调整文章顺序才主要是配置变化。架构的投入通过后续同类改动体现价值。

数学公式支持也并非只改一个文件就一定完成：编译依赖、样式和渲染验证仍有工作量。共享编译模块减少的是两套渲染逻辑各自维护、逐渐不一致的风险。

这些改动还需要构建、检查和部署。**修改范围缩小，与整个交付过程没有成本，是两回事。**

<h2 id="mechanisms">3. 隔离变化靠什么机制</h2>

### 信息隐藏：把可能变化的决定放到明确边界里

Parnas 在 1972 年的经典论文中讨论了模块应当如何划分：识别困难或可能变化的设计决定，再由模块封装这些决定，使其他部分不必依赖其细节。这是信息隐藏的重要思想。参见[论文出版页](https://doi.org/10.1145/361598.361623)及[原文的大学教学存档](https://www.cs.lafayette.edu/~gexia/cs301/resources/parnas.html)。

对 Wiki 来说，页面需要的是“可展示的文章列表”。文件位于哪个目录、怎样解析元数据、草稿怎样过滤、顺序怎样计算，可以由内容模块负责。

如果页面到处直接读取文件并解析元数据，存储方式或字段规则一变，就必须逐个修改调用者。把读取逻辑放进一个函数还不够：如果这个函数仍把文件句柄、内部路径规则等细节交给页面，依赖并没有真正消失。

信息隐藏关注的是**调用者是否必须知道内部决定**。它与 `private`、访问修饰符等语言机制有关，但不能仅靠这些语法完成。

### 高内聚、低耦合：让同类变化集中，让无关变化分开

可以用变化来理解这两个词：

- **高内聚**：共同维护一个职责的逻辑放在一起，例如排序配置的解释、缺省顺序和冲突处理。
- **低耦合**：一个职责的内部调整，不要求大量其他模块配合修改，例如文章排序不应要求正文渲染器知道排序配置格式。

这种边界也有取舍。如果首页以后强调“最新发布”，而学习目录强调“先修顺序”，两者的需求已经不同，就应允许不同排序策略。强迫所有页面共用同一个排序结果，反而会让一个页面的改动影响另一个页面。

复用应建立在相同的业务含义上；仅仅因为两段代码长得像，就把它们合并，也可能制造新的耦合。

### 稳定契约：约定行为，而不只是函数名

假设有一个文章读取接口：

```typescript
// 说明接口边界的示意代码，不是当前仓库的完整实现。
interface ArticleReader {
  getPublished(slug: string): Promise<Article | null>;
}
```

调用者还需要知道：什么算“已发布”、不存在时是否返回 `null`、读取失败怎样报错、结果包含哪些字段。列表接口则还可能需要约定排序、分页和一致性。

如果函数名和参数不变，行为却从“立即读到刚保存的文章”变成“可能读到几分钟前的缓存”，调用者的假设仍可能失效。**契约稳定包含语义稳定，必要时也包含调用者依赖的性能与一致性约束。**

### 依赖倒置与适配器：让业务逻辑少依赖外部技术

进一步设想，未来要把文章读取从文件迁移到数据库，可以让业务用例依赖自己需要的读取契约，由具体适配器实现它：

```text
源码依赖方向：

文章业务用例 ───→ 文章读取契约 ←─── 文件适配器
                            ←─── 数据库适配器
                            ←─── 测试替身
```

运行时，业务用例仍会调用注入的具体实现；图中的箭头表示源码依赖，不是运行时数据流。关键在于业务代码不直接依赖某个数据库 SDK 的类型和返回格式。依赖方向的讨论可参考 Robert C. Martin 的 [The Clean Architecture](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)。

Cockburn 的[六边形架构原文](https://alistair.cockburn.us/hexagonal-architecture)用端口与适配器描述这种内外分离：应用通过端口表达交互，适配器负责外部技术的转换，界面和数据库可以分别替换或用测试实现代替。

这个例子是可能的演进方案，不代表当前 Wiki 已实现完整的六边形架构。只有新实现满足既有契约，调用者才可能少改；数据迁移、错误处理、连接管理和运行验证仍然需要完成。

<h2 id="representation">4. jyy 的例子：用中间表示承接变化</h2>

课程还用“在 Excel 中生成二维码”的例子说明表示方式的价值：把计算组织成中间表示（IR），由后端生成目标程序或公式，并分别处理输入绑定、布局和兼容性。这样，不同变化更容易落到各自负责的部分。参见[《需求和架构（1）》的二维码示例](https://jyywiki.cn/GSE/2026/lect6.md)。

从这个例子可以得到一个设计启发：**好的抽象需要表达问题中相对稳定的结构，并明确哪些部分允许替换。**

例如，如果“计算什么”与“结果放在哪个单元格”混在一起，移动输出位置就可能触及算法公式。将计算与布局分别表达后，位置调整可以主要由布局部分处理。但如果新的计算无法被现有 IR 表达，就仍需扩展或调整 IR，抽象边界也要演进。

<h2 id="limits">5. 为什么只能抵御一部分变化</h2>

架构建立在一组假设之上：用户是谁、数据如何产生、哪些规则必须成立、部署环境能提供什么能力。它更容易承接那些仍然符合核心假设的变化。

以当前静态 Wiki 为例：

| 新需求 | 对现有设计的影响 |
| --- | --- |
| 新增文章、调整描述、改变顺序 | 大多可以由内容与配置处理 |
| 新增公式或代码块的展示能力 | 主要扩展编译与显示过程，但需检查兼容性 |
| 增加文章搜索 | 需要新增索引与搜索能力；范围取决于数据规模和更新方式 |
| 支持登录后查看私人文章 | 引入身份、授权和受保护的内容交付；不能只在公开页面里隐藏链接 |
| 多人同时编辑并实时看到彼此修改 | 引入共享状态、冲突处理、实时通信与持久化，原有静态发布假设发生明显变化 |

后两类需求可能需要引入后端或托管服务，并重新安排系统边界。已有的文章格式和部分渲染逻辑仍可能复用，但整体工作量不会因为有几个接口就消失。

还有一些变化涉及**业务含义与历史数据**。例如，原来的“发布日期”只有一个值，现在需要区分首次发布、最近修订和定时上线。若过去没有记录修订时间，新字段可以增加，缺失的历史事实却不能靠重构自动恢复。

因此，可替换的实现、可迁移的数据和可演进的业务模型是不同层面的问题。架构需要同时考虑它们，不能把所有变化都简化成“换一个适配器”。

<h2 id="evaluation">6. 用具体变化评估架构，而不是只看图</h2>

SEI 的《Modifiability Tactics》从耦合、内聚和成本等角度讨论可修改性：架构决策会影响系统应对修改的能力。参见 [SEI 官方报告](https://www.sei.cmu.edu/library/modifiability-tactics/)。

实践中，可以把“要易于扩展”改写成可检查的场景。下面是针对 Wiki 的自拟例子，时间与范围应由项目实际情况确定：

| 变化场景 | 希望保持的边界 | 怎样检查 |
| --- | --- | --- |
| 调整三篇文章的展示顺序 | 主要修改排序数据 | 所有需要该顺序的页面一致，其他文章仍可访问 |
| 增加公式渲染 | 预览与线上共享转换规则 | 同一篇样例文章在两处表达一致 |
| 换一种文章存储 | 页面不解析存储格式 | 新实现满足读取契约，迁移后文章与元数据完整 |
| 为阅读功能增加新界面 | 内容规则不散落到各界面 | 新界面复用用例，各入口遵循相同规则 |

评估时，除了改了多少行，还应记录：需要理解和修改哪些模块、是否涉及数据迁移、需要哪些团队协调、验证与上线要多久，以及出错后是否容易恢复。

有时改动文件不多，却改变了很多调用者共同依赖的语义；有时只是机械更新多个文件，风险反而较低。文件数可以帮助发现问题，不能代替影响分析。

<h2 id="evolution">7. 怎样避免为“未来变化”过度设计</h2>

隔离变化本身也有成本。每个接口、配置项和适配器都需要命名、理解、维护和验证。如果为了尚未出现的需求建立复杂插件系统，今天的简单改动可能先变得困难。

Fowler 对 [YAGNI](https://martinfowler.com/bliki/Yagni.html) 的解释强调：不要因为推测未来会需要某种功能，就立即把它做出来；这不排斥改善可修改性的重构、测试与持续交付。预测未来功能和维持代码健康，是不同的工作。

可以优先投入两类设计：

- **已有证据支持的变化**：文章持续增加、顺序需要调整、预览与线上必须一致。
- **后期纠正代价很大的决定**：数据含义、身份标识、历史保留、敏感内容的访问边界。

对于不确定且容易以后添加的能力，可以保留简单结构，在需求变清楚时再扩展。对于高影响的决定，先用小实验、数据样例或接口草案验证假设，比立即实现整套系统更有帮助。

演进也需要反馈。模块测试检查内部规则，契约测试检查实现是否遵守约定，关键集成检查确认它们组合后仍满足真实需求。测试范围应与改动风险相称，不必为每次内容修订增加一套测试。

Fowler 在 [Is Design Dead?](https://martinfowler.com/articles/designDead.html) 中讨论了测试、持续集成和重构如何支撑演进式设计。边界让修改更集中，这些实践则帮助确认修改后的系统仍然正确。

<h2 id="practice">8. 下次遇到需求变化，可以这样分析</h2>

1. **写出失效的假设。** 例如：“所有文章只需按日期排序”已经不成立。
2. **找到决定的拥有者和依赖者。** 检查规则是否重复，调用者是否知道过多内部细节。
3. **明确应保持的契约。** 哪些行为必须兼容，哪些行为确实要改变，历史数据怎样解释。
4. **让修改落到合适的职责里。** 必要时先整理边界，再实现需求；不要为了少改一行让规则进一步散落。
5. **验证并记录结果。** 检查实际修改范围、迁移和回归成本，简要记下设计理由与适用条件。

复习这句话时，可以用一个具体问题检验自己的理解：**如果明天需求沿这个方向变化，我能否指出主要改哪里、为什么其他部分能够继续成立，以及用什么证据确认它们仍然成立？**
