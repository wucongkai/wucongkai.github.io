**用指定的分词器把文本编码成一串编号，有多少个编号，就有多少个 token。** 700 token 并不是固定的 700 个字，也不是 700 个词。

系列阅读：[RAG 检索算法](/notes/rag-retrieval-algorithms/) · [框架与 GraphRAG](/notes/rag-frameworks-and-graphrag/) · 本文。

## 分词器怎样切分文本

分词器（tokenizer）使用词表、切分规则与预处理方式，将文本转成模型能处理的单位。一个单位可能是一个字、一个词、单词的一部分，或一个字符编码的部分字节。

```text
原文：我喜欢学习 AI
切分示意：[我] [喜欢] [学习] [ AI]
编号示意：[编号1, 编号2, 编号3, 编号4]
计数：4 个编号 → 4 token
```

**这只是示意，不是某个真实模型的分词结果。** 实际切法取决于分词器；空格、标点、换行、中英文混排都可能影响结果。同一文本换一个分词器，token 数也可能变化。

常见子词算法包括 BPE、WordPiece 与 Unigram。这里的“分词”不等于中文搜索系统里的按词切分：模型可能把一个中文词拆成多个单位。流程参见 [Hugging Face Tokenizers 文档](https://huggingface.co/docs/tokenizers/pipeline)。

## 怎样得到准确计数

应使用目标模型对应的分词器，并明确是否包含特殊 token、聊天模板等额外格式。对于已加载的匹配分词器，基本计数逻辑是：

```python
# tokenizer 应与目标模型匹配；此处只计算普通文本本身。
token_ids = tokenizer.encode(text, add_special_tokens=False)
token_count = len(token_ids)
```

模型对话通常还包括角色标记、消息边界或工具格式。因此“用户输入那句话的 token 数”与“完整模型输入的 token 数”可能不同。格式说明可参考 [Transformers 聊天模板文档](https://huggingface.co/docs/transformers/chat_templating)。

## Token 与 RAG 有什么关系

| 位置 | Token 的作用 | 注意事项 |
| --- | --- | --- |
| 文档切块 | 控制单块长度，例如目标 700 token | 计数依赖指定分词器，边界还应照顾段落与语义 |
| Embedding 输入 | 决定单次能编码多少内容 | 超长可能报错或截断，依模型实现而定 |
| 检索结果组装 | 限制能送入模型的证据量 | `top_k` 是条数，不是 token 数 |
| 生成输入与输出 | 共同占用模型支持的上下文与输出额度 | 还需为提示词、历史消息和答案留空间 |

Embedding 模型和生成模型可能使用不同分词器。切块时满足 embedding 的长度限制，并不意味着同一块送给生成模型时计数相同。

## 一个上下文预算示例

假设应用为某次调用设定了 **16,000 token 的可用总预算**，可以先这样分配：

| 内容 | 预算示例 |
| --- | --- |
| 系统提示、用户问题与历史消息 | 2,500 token |
| 检索到的证据 | 9,500 token |
| 预留输出 | 3,000 token |
| 格式开销与余量 | 1,000 token |
| 合计 | 16,000 token |

这些数字仅说明预算关系，不对应某个模型的固定上限。实际需遵守模型的上下文与输出限制，并考虑该接口如何计入其他 token。

因此，RAG 的最终证据选择不能只设“取前 6 条”：还应计算这些文本的总长度、去除重复、保留前提与来源，并为答案预留空间。相关流程见[RAG 检索算法中的上下文筛选](/notes/rag-retrieval-algorithms/#evaluation)。
